# Decisions

Append-only log of non-obvious technical decisions a future contributor would
otherwise re-litigate. Each entry: date — decision — reason. If a decision is
later reversed, add a superseding entry instead of editing the old one.

## Founding decisions (recorded retroactively on 2026-07-24)

- **Local LLM via Ollama instead of a hosted API** — data privacy for
  financial documents and zero per-call cost; the provider sits behind a
  `ModelProviderGateway` port, so swapping to a hosted API is a one-module
  change.
- **PostgreSQL + pgvector with an HNSW index** (`m=16, ef_construction=64`,
  cosine ops) — one database for relational data and vectors; HNSW chosen over
  IVFFlat for higher recall and no `ANALYZE`-after-population requirement.
- **Full Clean Architecture split** (domain / use cases / adapters /
  infrastructure) — deliberate learning exercise: the goal was to live with
  the full split long enough to see where it pays off and where it is
  ceremony. The lighter 3-layer split would suffice for this size otherwise.
- **Document row is persisted only after embeddings succeed**, and rolled back
  if chunk insertion fails — avoids orphan documents without requiring a
  cross-service distributed transaction.

## 2026-07-24

- **Coverage enforced in CI at ≥80% on the unit-test run** — threshold gives
  headroom below the current ~92% so a small refactor doesn't break the build.
  Integration tests run in a separate CI job (fast unit feedback; Docker pulls
  isolated), so their coverage does not count toward the threshold.
- **Coverage threshold raised to ≥90%** (supersedes the ≥80% entry above) —
  pinned to the current 92% rounded down to the nearest ten, keeping the gate
  close to reality while leaving a small refactor margin.
- **Static coverage badge (shields.io) instead of Codecov** — no external
  service or token for a small personal project; the number is updated
  manually when it moves materially.
- **English is the documentation language** for README and `docs/` —
  international-team standard.

## 2026-10-01

- **Paragraph breaks are rebuilt from line positions via pypdf's
  `visitor_text`** — plain extraction separates every line with a single
  `\n`, so paragraph and section boundaries inside a page were lost and whole
  pages went through the token splitter. The parser keeps plain mode's text
  and reading order and inserts a blank line where the baseline gap, in
  units of font size, exceeds 1.3x the page's tightest line spacing (capped
  at 1.8x), or where text jumps up the page (next column). Rejected:
  `extraction_mode="layout"` — it renders multi-column pages side by side,
  mixing both columns into every line; detecting `Section ...` lines inside
  paragraphs — misfires on wrapped body text ("...as required by / Section
  404 of the Act"). Limitations: thresholds are heuristic, double-spaced
  text degrades to one paragraph per line, and the parser is verified on
  fpdf2-generated PDFs only.
- **A section heading closes the running chunk, with no overlap carried
  across** — a short heading otherwise fits into the previous section's tail
  and relabels that whole chunk. A section boundary is a topic boundary, so
  overlap there only dilutes the new section's embedding. Leftovers under
  `min_chunk_tokens` (e.g. a title page) join the next section instead.
- **Untrusted prompt spans are fenced in XML-like tags and escaped** —
  document chunks, chat history and the question go inside `<documents>`,
  `<chat_history>` and `<question>`, with the instructions last and marked
  as taking precedence. `<`, `>` and `"` are HTML-escaped so text cannot
  forge or close a tag; role markers (`SYSTEM:` at line start) and
  "ignore previous"-style phrases are wrapped as `[quoted: ...]` rather than
  deleted, keeping them inspectable. Defence in depth, not a guarantee.
- **Ollama calls retry 429/5xx and connection errors, not timeouts** — up to
  3 attempts with exponential backoff from 0.5 s plus up to 50% jitter
  (tuning, not law). Bounded attempts serve as the circuit breaker for the
  embedding batch loop, which aborts on the first call that exhausts them.
  Timeouts are not retried because a 120 s generation timeout would turn
  into minutes of waiting.
- **Embedding dimension comes from `EMBEDDING_DIM`, not the schema** —
  `001_init.sql` sizes `chunks.embedding` with a psql variable that
  `migrations/apply.sh` (the container init script and `make migrate`) sets
  from the environment; integration tests apply the same files. The API
  verifies the column's `atttypmod` against the setting at startup and the
  repository checks each vector's length, so a model/schema mismatch fails
  with a message naming the setting instead of an opaque pgvector error.
  Changing the dimension of an existing database still needs a migration.
- **Tests mirror the source tree and are packages** — `tests/infrastructure/`,
  `tests/use_cases/`, `tests/adapters/api/` follow `src/findocbot/`; app-level
  smoke tests map to `main.py` (`tests/test_main.py`) and the cross-cutting
  RAG evaluation stays at the root. `__init__.py` files make same-named
  modules safe across directories and let shared helpers import as
  `tests.factories` / `tests.use_cases.fakes` instead of being copied.
- **CI runners pinned to `ubuntu-24.04`, not `ubuntu-latest`** — GitHub
  moves `ubuntu-latest` to Ubuntu 26 from 2026-10-19; pinning keeps the
  runner OS from changing under an unrelated push. Bump it deliberately in
  its own commit.

## 2026-10-04

- **Ollama calls retry every `httpx.TransportError`, still not timeouts** —
  supersedes the "connection errors" entry above. A connection dropped
  mid-generation (`ReadError`, `RemoteProtocolError` on an Ollama restart)
  is as transient as a refused one and used to escape as a 500. The
  timeout branch stays first because `TimeoutException` is a
  `TransportError` subclass.
- **Unreadable PDF bytes are a 400, not a 500** — the parser maps
  `pypdf.errors.PyPdfError` to `InvalidDocumentError` (a `FinDocBotError`)
  so a client sending garbage with `application/pdf` gets a client error.
- **A missing or `None` LLM answer is a 502, same as a non-string one** — it
  used to slip through as an empty answer and be stored in chat history,
  from where it was fed into every later prompt of the session.
- **502 responses carry a fixed message, the provider error goes to the
  log** — `ModelProviderError` text names Ollama's internal URL, which a
  client has no use for.
- **ruff pre-commit hooks run `uv run ruff`, not `ruff-pre-commit`** — the
  external repo pinned its own ruff (0.12.8 vs 0.15.0 in `uv.lock`); with
  `preview = true` formatting can differ between versions, and the hook and
  CI would then disagree.
- **Generation sends `num_ctx=16384` and `num_predict=1024`** — without
  them Ollama uses its server default context and cuts longer prompts from
  the start, which drops the retrieved sources without an error. Worst case
  is ~12k tokens: 20 chunks (`top_k` max) x 300 tokens, 5 history pairs of
  up to 4000 chars (~1k tokens each), the question and instructions. The
  answer cap keeps one call bounded; `/api/embed` gets no options, chunks
  already fit the embedding model's window.
- **Logging is configured in `create_app` only when it builds the
  production container** — root stays at `WARNING` and only the `findocbot`
  logger follows `LOG_LEVEL`, since httpx logs every Ollama request at
  `INFO`. Tests inject a container and keep pytest's logging untouched.
- **`/health` checks PostgreSQL and Ollama and answers 503 when either is
  down** — a process-only check reported healthy while every request
  failed with 503. One endpoint, no liveness/readiness split: nothing
  restarts the container on a failed check yet; if an orchestrator does,
  split off a cheap liveness route so a DB outage doesn't cause restarts.
  The checks are wired in the container rather than added to the
  `ModelProviderGateway` port, which use cases don't need for this. The
  Ollama ping skips the retry loop: a probe should report, not wait.
- **The server issues `session_id`; `/ask` rejects ids it did not issue
  with 404** — a client-chosen id let anyone who guessed it (README used
  `user-session-123`) have the model recount another dialogue or plant
  turns in it. Ids are `secrets.token_urlsafe(32)`, stored in `sessions`.
  The row is created only after the first answer succeeds, so a failed
  call leaves nothing the client never got an id for. No FK from
  `chat_turns`: turns from before the change carry unissued ids and stay
  unreachable. This is not user isolation — there is no auth and documents
  stay shared; a future `user_id` column on `sessions` would add that.
- **Follow-up questions are rewritten by the LLM before retrieval** —
  embedding only "And net profit?" searches without the topic it refers to.
  Chosen over concatenating the previous question (drags retrieval to the
  old topic) and over two searches merged by score (cheap, but helps less).
  Cost: one extra generation per follow-up, seconds on local Ollama, about a
  minute on CPU in Docker; first questions are unaffected. The rewrite
  prompt follows the same safety layout as the answer prompt; its output
  goes only to the embedder, and a malformed reply falls back to the
  original question rather than failing the request.
- **Uploads are deduplicated by SHA-256 of the raw bytes; a duplicate
  returns the stored document with 200, not 409** — two copies of one PDF
  fill `top_k` with identical chunks. Re-uploading is then idempotent and
  costs no parsing or embedding. Raw bytes, not extracted text: the same
  report re-exported to a new PDF counts as a new document, accepted as
  the simpler rule. The response is the stored document, so its filename
  is the first upload's. Rows from before `004` have no hash; duplicates
  among them stay until deleted.
- **`GET /documents`, `GET`/`DELETE /documents/{id}` go through one
  `ManageDocumentsUseCase`** — three one-line use-case classes would be
  ceremony. Delete relies on `ON DELETE CASCADE` to drop the chunks; the
  in-memory fakes don't model the cascade, so that part is covered by an
  integration test. Ids are typed `UUID` in the path, so a malformed id is
  a 422 instead of a Postgres type error surfacing as 503. Not-found cases
  share a `NotFoundError` base mapped to 404.
- **Image and tool versions are pinned: `ollama/ollama:0.35.1`,
  `uv==0.12.11` in the Dockerfile** — `latest` and an unpinned `pip install
  uv` made the build depend on the day it ran. The Ollama tag is the one the
  end-to-end runs used (same digest as the `latest` pulled 2026-10-02).
  Neither is bumped by Dependabot; update them by hand.
- **Dependabot uses the `uv` ecosystem, minor and patch grouped** — under
  `pip` it opened no Python PR in eight months while `fastapi` and others
  fell behind; the `>=` ranges in `pyproject.toml` were always satisfied and
  `uv.lock` was never read. Grouping keeps the first run from opening a PR
  per package.
- **Pydantic is allowed in use cases, for validating model output** — two
  rules disagree: `clean-architecture.md` flags framework imports in use
  cases, while `python-core.md` and `ai-engineering.md` ([MUST]) ask for
  Pydantic schemas to validate LLM output. The validation is a use-case
  rule (what counts as a usable answer), and Pydantic is a validation
  library, not a delivery or persistence framework, so `answer_question.py`
  keeps it. The domain layer stays stdlib-only.
- **The PDF parser also maps pypdf's builtin exceptions to a 400** —
  fuzzing 1500 corrupted copies of two PDFs (byte flips, truncation, cut
  ranges; seed 20261004) gave 122 raw `KeyError`, `AttributeError`,
  `NotImplementedError`, `TypeError`, `ValueError`, `IndexError` and
  `UnboundLocalError` from pypdf internals, each a 500. The catch list is
  exactly what was observed, not `Exception`. It can also hide a bug in our
  own extraction visitor as a 400, so that branch logs the traceback.
- **Ollama timeout, pool size and chunker parameters are settings** —
  they differ by deployment (CPU generation in Docker needs a longer
  timeout) and were editable only in code. Retry count and backoff, the
  `/health` probe timeout and the per-span prompt limits stay constants:
  they are tuned to the code around them, not to the environment.
  `CHUNK_TOKENS` is coupled to `OLLAMA_NUM_CTX` and `_MAX_SOURCE_CHARS`;
  `.env.example` says so next to it.
- **Routes depend on an `ApiServices` Protocol; repository fakes moved to
  `tests/in_memory.py`** — `routes.py` imported `AppContainer`, so the
  adapter layer depended on the infrastructure composition root, and the
  fakes shipped in the production package. `main.py` stays the only place
  that knows the container. Behaviour is unchanged.

## 2026-10-07

- **Upload ingestion runs in a background in-process queue, not in the
  request** — a 50 MB PDF can take minutes to embed on CPU-Ollama, too long
  for a synchronous `POST /documents/upload`. The route now stores a
  `pending` document, enqueues the bytes, and returns `202`; one worker task
  drains a bounded `asyncio.Queue` and flips the document to `ready` or
  `failed` (with a client-safe `error`; provider-internal messages never
  reach the stored error). Chosen over Celery/RQ: no broker to run, and the
  in-process worker still exercises background processing. The trade-off
  is that queued bytes live in memory and are lost on restart, and parsing
  errors that used to be a synchronous `400` now surface as `failed`
  documents. Re-uploading the same bytes returns the stored document (`200`)
  instead of queueing again.
- **Migrations moved to Alembic with raw-SQL revisions** — `apply.sh`
  re-ran every numbered `.sql` file with no version table, so a shipped file
  could not be edited safely. Alembic records applied revisions in
  `alembic_version`; `make up` runs `alembic upgrade head` in the `api`
  service, `make migrate` runs it locally, and the integration tests drive
  the same revisions. Migrations connect over the psycopg driver (a new
  dependency) while the runtime pool stays on asyncpg; `0001` sizes
  `chunks.embedding` from `EMBEDDING_DIM` exactly as the old psql variable
  did.
- **`postgres_dsn` has no default; DB and Ollama ports bind to loopback** —
  the settings default hardcoded a `postgres:postgres` password, and compose
  exposed Postgres and Ollama on all interfaces. `postgres_dsn` is now
  required (read from env / `.env`), and both ports are `127.0.0.1`-bound so
  nothing is reachable beyond the host.

## 2026-10-15

- **Tests move to a three-layer layout (`tests/unit|integration|e2e`)** — the
  vendored `testing.md` now mandates splitting tests by the I/O they need, so
  each layer (`unit` = no I/O, `integration` = real Postgres, `e2e` = HTTP
  surface) mirrors `src/findocbot/` within itself. Shared helpers
  (`tests/factories`, `tests/in_memory`, `tests/fakes`) stay at the `tests/`
  root. Supersedes the 2026-10-01 "tests mirror the source tree" entry: the
  mirror is now within each layer, not the top-level layout. True end-to-end
  (real DB + real Ollama through HTTP) remains future work — `tests/e2e/`
  currently holds the `ASGITransport` tests.

- **A real end-to-end test lands (`tests/e2e/test_end_to_end.py`)** — gated by
  `@pytest.mark.e2e` / `--e2e`, it spins up a real Postgres (testcontainers) and
  a real Ollama (`nomic-embed-text` + `qwen2.5:0.5b`, pulled at test start), then
  drives upload → poll → search → ask through the HTTP surface. CI runs it in a
  dedicated `e2e` job (the slow one — the model pull is ~670 MB). Supersedes the
  "remains future work" note above.

- **The e2e `/ask` test asserts the cited sources, not the answer text, and the
  embed model is pinned to `nomic-embed-text:v1.5`** — a 0.5B model sampled at
  Ollama's default temperature words its answer differently on every run, so
  only retrieval is deterministic: the sample's revenue figure must appear in
  `sources`. A 200 still needs the model to emit valid JSON, so the test can
  still flake with a 502. A seed or temperature setting would remove that, but
  it is a `Settings` field with no consumer outside this test, so it was left
  out. `Settings` defaults to `nomic-embed-text:latest`; the test pins the tag
  so a re-pushed model cannot shift retrieval under the assertion.
- **Each e2e test ingests the sample PDF itself and the database is truncated
  before every test** — one shared ingested document would save a few seconds
  per test but needs module-scoped async fixtures (pytest-asyncio
  `loop_scope`) and a connection pool that outlives each test's event loop.
  Isolation was worth more than the seconds.
- **CI actions are pinned by commit SHA; the coverage action is pinned to the
  moving `v3` tag as it resolved on this date** — that commit sits 65 commits
  past the last v3 release (`v3.41`) and 46 before `v4.1`, with no release tag
  of its own. Pinning it keeps the code CI already ran, where `v3.41` would
  quietly step back. Move to a tagged release when it is worth reviewing the
  change. Bump SHA and trailing version comment together.

- **Ingestion is one module with a private queue; the queue port is gone** —
  `UploadPDFUseCase`, `InProcessUploadQueue` and `UploadQueuePort` became
  `IngestionUseCase`. Dedup, the worker, every status transition and error
  sanitising were spread over four modules joined by a circular
  `set_processor` call that the container and two test builders each
  repeated; the port had one production adapter and one test double, which
  is a hypothetical seam. The queue stays in-process (2026-10-07 entry) but
  is now stdlib `asyncio` inside the use case: a data point for the Clean
  Architecture exercise, where this port turned out to be ceremony. The
  refactor changes no behaviour; `drain()` remains the test hook and
  `stop()` still drops unprocessed jobs. Five defects in this path are
  filed as #36–#40, each to be fixed on its own, with tests that pin
  today's behaviour (`tests/e2e/test_routes.py`) so each fix flips an
  assertion on purpose.
- **A document row is now written as `pending` before any parsing, and a
  failed ingestion marks it `failed`; nothing is rolled back** — supersedes
  the founding entry "document row is persisted only after embeddings
  succeed, and rolled back if chunk insertion fails", which stopped being
  true when ingestion moved to the background queue (2026-10-07).

- **An unexpected error during ingestion marks the document `failed` with a
  fixed message, `Ingestion failed unexpectedly.`** — it used to leave the
  document `pending` for ever, with the worker logging and moving on (#36).
  `IngestionUseCase._process` now has a deliberately broad `except Exception`
  after the `FinDocBotError` branch: it is the outermost boundary of a
  background job with no caller to report to, and `python-core.md` asks for
  specific exception types elsewhere. It logs the traceback; the stored text
  is a constant, never the exception's own message, so driver and parser
  internals stay out of `documents.error` as the 2026-10-04 "502 responses
  carry a fixed message" entry does for the API. The text does not suggest
  re-uploading, because a re-upload returns the same failed document (#38).
  The worker's own catch-all stays as the last resort for a failure the
  status update itself cannot record. `asyncio.CancelledError` is not caught,
  so a shutdown mid-job still leaves the document `pending` (#37).

- **`submit` reports whether it queued ingestion, and the route answers 202
  only then; any duplicate answers 200** — the 2026-10-04 entry and the README
  already say a duplicate returns 200, but since ingestion moved to the
  background (2026-10-07) the route read `document.status`, so a duplicate of a
  still-`pending` upload got 202 (#39). `IngestionUseCase.submit` now returns a
  `Submission(document, queued)`; the pre-check hit and the concurrent-insert
  race both report `queued=False`. The flag says "queued", not "new", so a
  future retry of a `failed` document on re-upload (#38) can queue it and answer
  202 without changing the route's rule.

- **Search only considers chunks of `ready` documents, enforced in the search
  query** — chunks are committed before the document is marked `ready`, so for
  a moment, and for good if that update fails, a `pending` or `failed`
  document's chunks answered questions (#40). `search_by_embedding` now joins
  `documents` and filters on status, so "searchable" is defined in one place
  and matches `CONTEXT.md`. Chosen over committing the chunks and the status
  in one transaction: that needs one operation spanning the document and chunk
  repositories and wiring the in-memory fakes together, where this touches one
  query. Trade-offs: pgvector filters after the HNSW scan, so `top_k` can
  return fewer rows when many of the nearest chunks belong to non-ready
  documents (checked on 10,000 chunks with 10% non-ready: the index is still
  used and the full count returns); chunks of a `failed` document stay stored
  until it is deleted, so a retry on re-upload (#38) has to clear them first;
  and the in-memory chunk repository has no document status, so the rule is
  covered by integration tests only.

- **Re-uploading a `failed` document retries it; a `pending` or `ready` one is
  still returned as it is** — a transient failure (Ollama down while
  embedding) otherwise made that content permanently stuck until the client
  deleted it (#38). Supersedes the part of the 2026-10-04 dedup entry that
  says a re-upload costs no parsing or embedding: for a `failed` document it
  now does, and a deterministic failure such as an unreadable PDF is
  re-parsed on every re-upload (bounded, accepted). `submit` claims the retry
  with `DocumentRepositoryPort.reset_failed`, one conditional `UPDATE ... WHERE
  status = 'failed'`, so concurrent re-uploads queue it once; the loser
  re-reads the row and reports `queued=False`. Only `failed` is retried: a
  `pending` document may really be in flight, and one stranded by a restart
  cannot be told apart from it (#37). The ingestion job replaces the document's
  chunks in one transaction (`replace_document_chunks`, replacing
  `add_chunks_with_embeddings`), because chunks have no uniqueness on
  `(document_id, chunk_index)` and the failed attempt may have left some (see
  the ready-only search entry), which would otherwise come back as duplicates.

- **A restart marks documents it left `pending` as `failed`, with "Ingestion
  was interrupted by a restart; upload again."** — the ingestion queue is in
  memory (2026-10-07 entry), so after a crash or a restart the queued bytes are
  gone and their documents stayed `pending` for ever (#37). Chosen over
  persisting the bytes, which that entry rejected to avoid a broker and a
  durable store. `IngestionUseCase.recover_interrupted` runs as a startup step
  (`startup_checks`: after the database is up, before the worker starts; a
  failure aborts startup like the schema check) rather than inside `start()`,
  which would hide a state change in a lifecycle call and, after a `stop()`,
  fail jobs still waiting in the queue. The message says "upload again"
  because a re-upload of a failed document is now a retry (#38), where the
  unexpected-error message deliberately did not suggest it. This also covers a
  shutdown that cancelled a job mid-way. Assumptions, accepted: one API
  instance (a second instance starting would fail the first one's in-flight
  documents, and the first one's worker would later overwrite that with
  `ready`), and every `pending` row at startup belongs to a process that is
  gone.

- **Coverage is measured over the unit and integration suites together, in the
  `test` job, and the threshold lives in `pyproject.toml`** — supersedes the
  2026-07-24 entries that enforced it on the unit run alone (≥80%, then ≥90%)
  and kept the integration job apart. The PostgreSQL repositories and `db.py`
  are exercised only by integration tests, so the unit-only figure counted
  about a hundred statements it could never reach and had settled 0.22 points
  over the gate; the next ordinary change would have turned CI red. Together
  the suites reach 95.9%, and `fail_under = 93` leaves about three points of
  headroom. It is the one place the number is written (CI runs `make cover`,
  which reads it), so `--cov-fail-under` is gone from the workflow, and the
  separate `integration` job is gone too: the `test` job runs the same tests.
  The "main protection" ruleset on `master` required a check named
  `integration`, which no longer reports, so its required checks are now
  just `test`; put the two back together if a job of that name returns.
  Unit-only feedback stays `make test`; `make cover` now needs Docker. The e2e
  job is not counted (it needs a real Ollama). Chosen over merging coverage
  files from parallel jobs, which keeps the jobs apart but needs artifact
  upload and download steps and a combining job. Raise the number as coverage
  grows; never lower it to go green. The repository ruleset `main protection`
  (a GitHub setting, not in this repo) required the checks `test` and
  `integration`; with the `integration` job gone it now requires `test` only,
  and that job carries the integration tests.

- **The e2e fixture retries `ollama pull` (3 attempts, pausing 10 s then 20 s)
  and reports the registry's own error line** — the Ollama registry is an
  external service; one `e2e` run failed on `503: upstream connect error`
  before any test ran and passed on a rerun. The retry lives in
  `tests/ollama_pull.py` rather than inline so it can be unit-tested with a
  fake container and an injected pause (no `time.sleep` in the tests). The exit
  code stays checked, which the container library's own `pull_model` does not
  do. Every failure is retried, a misspelled model included, which costs about
  half a minute before it fails; the job's 20-minute timeout bounds the worst
  case. The error message is the last line of the pull output, not the raw
  spinner bytes the pull prints while it redraws.

- **A reranker is evaluated before it is built: `evals/` compares vector
  retrieval with and without one, and the first run says to try prefixing the
  document title first** — the candidate is the community GGUF of
  Qwen3-Reranker-4B (`awenleven/Qwen3-Reranker-4B:Q4_K_M`). Ollama has no
  rerank endpoint, so the harness drives it through `/api/generate` in raw mode
  with the Qwen prompt and reads P(yes) from the first token's `logprobs`
  (every case variant of yes/no summed; a first probe that kept only the last
  variant gave wrong rankings). First run, 2026-10-15, on a synthetic corpus of
  18 reports (108 chunks) and 40 frozen questions, top-20 pool:
  with chunks as stored the reranker lifts hit@1 from 24/40 to 28/40, hit@5
  from 26/40 to 36–39/40 and MRR from 0.64 to 0.78–0.79, but only on the two
  categories whose chunks name neither company nor year (it ties at 8/8 on the
  other three); with the document title prepended to every chunk, plain vector
  search already reaches 38/40 at hit@1 and 40/40 at hit@3, and the reranker
  adds the last two (40/40). So most of what a reranker buys here is a missing
  context problem with a cheaper fix. Cost: about 0.4 s per pair, so roughly
  9 s for a 20-candidate query on this machine (an earlier 5-chunk probe saw
  0.11 s; not explained). **Indicative only**: the corpus and questions were
  written by the project, n is 8 per category, the pool is 18% of the corpus,
  and the "title" is the PDF file name, which real files rarely make useful.
  Nothing in `src/` changed; the next step is the same evaluation on real PDFs
  and questions where retrieval fails (`evals/README.md`).

- **Reranking is an opt-in step inside search, off until `OLLAMA_RERANK_MODEL`
  is set** — the manual evaluation in `evals/` (synthetic corpus, first run
  2026-10-15) showed a reranker mostly compensates for chunks that name
  neither company nor year, which prefixing the title fixes more cheaply, so
  it ships switchable and off by default until real documents say
  otherwise. `RerankerPort` is a separate, narrow port (not another method on
  `ModelProviderGateway`); `OllamaReranker` drives the community GGUF of
  Qwen3-Reranker through `/api/generate` in raw mode, because Ollama has no
  rerank endpoint, and reads P(yes) from the first token's `logprobs`
  (needs a recent Ollama). It opens a client per `rerank` call, so it has no
  lifecycle to start or stop. Failure policy: a `ModelProviderError` or a
  deadline of `RERANK_TIMEOUT_SECONDS` keeps the vector order and logs a
  warning, since search without reranking is still correct. The result `score`
  is the reranker's P(yes) when reranking ran, the cosine similarity
  otherwise. Not retried and not cached: a retry would add whole seconds to a
  query that already costs about 0.4 s per candidate. Built test-first at
  three seams (the adapter against a faked Ollama, the search use case with a
  scripted reranker, and `/search` and `/ask` over HTTP), plus an integration
  test of the container wiring against real Postgres. The first run
  against the real local Ollama found what the fakes could not: without an
  explicit `num_ctx` the community GGUF loads with its 40200-token window
  and an 8.7 GB runner (3.8 GB at 8192), which on a 16 GB machine shared with
  other models made a 20-candidate query take minutes instead of about 13 s.
  The adapter now sets `num_ctx` to 8192.

- **The reranker stays off by default after the real-document runs; the
  embedder is the next thing to evaluate** — the same harness on three public
  annual reports (`evals/documents.md`, 14 questions each, top-20 pool,
  2026-10-15) gives hit@1 vector → rerank of 5/14 → 10/14 on the English
  report (547 chunks, MRR 0.50 → 0.79), 3/14 → 9/14 on the Russian one (130
  chunks, MRR 0.32 → 0.64) and 1/14 → 9/14 on the Armenian one (59 chunks, MRR
  0.19 → 0.65). On Russian and Armenian the reranker already reaches the
  ceiling set by the pool (the gold chunk is in the top 20 for 9/14 and 10/14
  questions), so candidate recall of `nomic-embed-text` is what limits
  those languages, not the ordering. A multilingual embedder (bge-m3 or
  qwen3-embedding) is the next run; it changes `EMBEDDING_DIM` and needs a
  re-embed, so it is not a settings flip. Default stays off because turning it
  on costs a 2.5 GB model and seconds per search (about 0.7 s per candidate
  idle on an M1 Pro; the Russian and Armenian runs shared the machine with
  other jobs and show 2–5 s per pair, which is contention, not the model);
  whether to flip it is the project owner's call. **Indicative only**: the
  questions were written by the project, n is 14 per language, and the
  Armenian ones have not been reviewed by a native speaker. The `default` and
  `task` instruction variants give the same result within noise.
